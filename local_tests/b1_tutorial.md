## 0 一句话结论

题目要的是：**手写解析器，把十进制字符串转成 32 位有符号整数；在乘法溢出发生**之前**拦住超界输入；成功才写 `output`，失败时 `output` 必须原样不动。**

核心是一个不等式：

> 若 `value > (limit - digit) / 10`，则再执行 `value = value*10 + digit` 必然越界 → 立刻返回 false。

这样整条链路上 `value` 从未超过 `limit`，**永远不会溢出**，也就不需要"事后补救"。

## 2 接口与数据含义

```cpp
bool parse_i32(const std::string& text, int& output);
```

| 名称 | 类型 | 含义 |
| --- | --- | --- |
| `text` | `const std::string&` | 待解析文本，长度 ≤ 1000，只读 |
| `output` | `int&` | **引用输出**：成功时写入结果，失败时必须保持原值 |
| 返回值 | `bool` | `true` 成功，`false` 失败 |

`int&` 是**引用参数**——它和调用方的变量是同一个对象，不是副本。所以 `output = ...` 会真正改写调用方的变量。这也正是规范 4"失败时 output 保持不变"需要显式遵守的原因：函数什么都不写，它自然就保持不变。

用 `long long` 作为内部累加器，而不是 `int`：这样即使中间值短暂接近边界，也不会在 32 位上溢出；最后再转回 `int`。

## 3 规范逐条拆解

| 题面规范 | 翻译成代码动作 | 最容易踩的坑 |
| --- | --- | --- |
| 1 长度 ≤ 1000；可选单符号 + 至少一位数字 | 先判 `empty`/长度，再处理符号，再判符号后是否还有字符 | 空串、`"+"` 漏判 |
| 2 前导零、`+0`、`-0` 合法；空白/小数点/第二符号/非 ASCII 数字/尾缀均非法 | 逐字符 `ch < '0' \|\| ch > '9'` 检查 | 用 `isdigit(ch)` 可能接受本地化字符；用 `cin >>` 会放空前导空白 |
| 3 范围 `[-2147483648, 2147483647]`，含两端点 | 负号时 `limit=2147483648`，正号时 `limit=2147483647` | 两边都用 2147483647 → 漏掉最小负数 |
| 4 成功写 output 返回 true；失败返回 false 且 output 不变 | 所有检查通过后才写 `output` | 边解析边写 output，失败时已污染 |
| 5 禁用转换库；溢出前拒绝 | 用 `(limit - digit)/10` 预判 | 先 `value*10+digit` 再检查（已经溢出了） |
| 6 `O(len)` 时间、`O(1)` 空间 | 单次线性扫描，几个局部变量 | 用 `reverse` 再加额外缓冲区 |

## 4 核心一：为什么范围不对称

32 位有符号整数的范围是：

```
最小负数 -2147483648   （绝对值 2147483648）
最大正数  2147483647
```

负数的绝对值比正数**多 1**。所以不能统一用 2147483647 做上限：

```cpp
const long long limit = negative ? 2147483648LL : 2147483647LL;
```

若两边都用 2147483647，`"-2147483648"` 会被误判为超界，而它恰恰是题面样例第一条要求合法的输入。

同理，不能在最后写 `if (value > 2147483647) return false;` チェック正数——那会把合法的最小负数挡掉。用按符号区分的 `limit` 一次解决。

### 为什么用 `long long` 比较

`limit` 和 `value` 都声明为 `long long`，所以下面的比较与减法都在 64 位上进行，不会在判断阶段自己先溢出。转成 `int` 只在**所有检查都通过之后**发生：

```cpp
output = static_cast<int>(negative ? -value : value);
```

此时 `value ∈ [0, 2147483648]`，取负后落在 `[-2147483648, -0]`，全都在 `int` 范围内。

## 5 核心二：溢出前拦截的数学

朴素写法是"先算再查"：

```cpp
value = value * 10 + digit;      // 这一步可能已经溢出
if (value > limit) return false; // 太迟了
```

在 C++ 中，有符号整数溢出是**未定义行为**——编译器可以做任何事，包括让检查失效。

正确写法在乘法之前判断：

```cpp
if (value > (limit - digit) / 10) return false;
value = value * 10 + digit;
```

推导：设下一步要算 `v' = 10v + d`，要求 `v' ≤ limit`。移项得 `v ≤ (limit - d) / 10`（整数除法向下取整正好容纳等号）。若当前 `v` 已超过这个上界，则 `v'` 必然越界，直接拒绝。

由于 `limit - d` 用 `long long` 计算且 `d ≤ 9`，不会出现下溢。整个过程中 `value` 始终 ≤ `limit`，安全不变量成立。

### 逐字符跟踪 `-2147483648`

| 步骤 | 字符 | `value` 更新 | 是否触发拦截 |
| --- | --- | --- | --- |
| 读符号 | `-` | `negative=true`, `limit=2147483648` | — |
| 1 | `2` | 2 | 否 |
| 2 | `1` | 21 | 否 |
| … | … | … | 否 |
| 9 | `4` | 214748364 | 否 |
| 10 | `8` | 2147483648 | 否（恰好等于 limit） |
| 结束 | — | 写 `output=-2147483648` | 成功 |

最后一步的判定：`value=214748364`，`digit=8`，`(limit-digit)/10 = (2147483648-8)/10 = 214748364`，`value` 不大于它，所以允许。若是 `"-2147483649"`，`(limit-9)/10 = 2147483639`，当前 `214748364 > 2147483639`，拦截。

## 6 完整参考实现

```cpp
bool parse_i32(const std::string& text, int& output) {
    if (text.empty() || text.size() > 1000) return false;

    std::size_t i = 0;
    bool negative = false;
    if (text[i] == '+' || text[i] == '-') {
        negative = (text[i] == '-');
        ++i;
    }
    if (i == text.size()) return false;      // 只有符号，没有数字

    const long long limit = negative ? 2147483648LL : 2147483647LL;
    long long value = 0;
    for (; i < text.size(); ++i) {
        const char ch = text[i];
        if (ch < '0' || ch > '9') return false;      // 非 ASCII 数字
        const int digit = ch - '0';
        if (value > (limit - digit) / 10) return false;  // 溢出前拦截
        value = value * 10 + digit;
    }

    output = static_cast<int>(negative ? -value : value);
    return true;
}
```

关键点：

- 前导零自然处理：`"0000123"` 每次 `value = 0*10+d`，最终得 123。
- `"+0"`、`"-0"`：`value` 保持 0，取负还是 0。
- 所有失败路径都 **return false 且不写 output**——只有函数末尾那一句赋值。
- 用 `ch < '0' || ch > '9'` 而非 `isdigit(ch)`：后者受 locale 影响，且接受 `unsigned char` 范围内的其他字符；题面明确要求 ASCII 数字。

## 10 缺陷定位与修复（README 素材）

本参考实现一次通过，但差分测试的第一轮出现了 1408 处"不一致"，值得记录：

| 阶段 | 现象 | 定位 | 修复 |
| --- | --- | --- | --- |
| 第一轮差分 | `" 1"`、`"1 "` 等 1408 组报不一致：实现返回 `true`，参照返回非法 | 检查**测试驱动**发现用的是 `cin >> s`——它会跳过前导空白、把尾随空白当分隔符，字符串在送达被测函数前就被改写了 | 驱动改用 `getline` 逐行读取原始字符串；重新跑 2500 组，0 不一致。实现无需改动 |

这段的价值与前面几题同类：**测试失败先怀疑测试框架**。题面规范 2 明确"禁止任何空白"，实现用 `ch < '0' || ch > '9'` 已经正确拦截；问题出在驱动层把空白吃掉了，导致被测函数收到的根本不是原字符串。定位方法是打印一条失败用例的原始字符串与实际入参，发现两者不同。

另一个防御性要点：用 `static_cast<long long>` 定义 `limit`，避免 `2147483648` 这个字面量在 32 位 `int` 上无法表示而触发编译器警告或截断。

## 11 常见错误对照表

| 错误写法 | 后果 | 正确做法 |
| --- | --- | --- |
| `limit = 2147483647` 用于负数 | 最小负数被误判非法 | 按符号选 limit |
| `value*10+digit` 后再检查 | 已溢出，未定义行为 | 用 `(limit-digit)/10` 预判 |
| 用 `int` 做累加 | 中间值溢出 | 用 `long long` |
| `isdigit(ch)` | 受 locale 影响 | `ch >= '0' && ch <= '9'` |
| 用 `stoi` / `stringstream` | 违反规范 5 | 手写逐字符解析 |
| 边解析边写 `output` | 失败时污染输出变量 | 只在函数末尾写一次 |
| 漏判空串 / 单独符号 | 越界读 `text[0]` 或误成功 | 开头与符号后各判一次 |
| 允许多个符号 | `++1` 被误收 | 只处理第一个字符的符号 |
| 用 `std::reverse` 辅助 | 违反 O(1) 空间 | 从左到右单次扫描 |

## 12 复杂度

- **时间**：`O(len)`，单次线性扫描，最多 1000 个字符。
- **空间**：`O(1)`，只有 `i`、`negative`、`limit`、`value`、`digit` 几个局部变量。
- **数值**：`value ≤ 2147483648`，`limit - digit ≥ 2147483638`，除法与乘法都在 `long long` 范围内，无溢出。
