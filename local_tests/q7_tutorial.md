## 0 一句话结论

题目要的是：**逐帧仿真，每帧固定第一步先冷却，再看请求；请求为 1 时只有弹量充足且冷却后热量加射击热量不超 100 才真正发射，否则只记一次拒绝。**

一帧的判定顺序不能换：

> **冷却 → 判请求 → 判资格 → 提交（或只计数）**

换顺序会改变结果：先判热量再冷却时，`simulate(1,100,20,20,{1})` 会被拒绝；按题面先冷却再判，则允许发射。题面背景里"我明明按了开火"的争论就是这件事。

## 2 接口与数据含义

```cpp
struct FireResult { int shots; int rejected; int ammo; int heat; };
FireResult simulate(int ammo, int heat, int cool, int shot_heat, const std::vector<int>& requests);
```

| 名称 | 类型 | 题面保证 | 含义 |
| --- | --- | --- | --- |
| `ammo` | `int` | 初始弹量，[0,100] | 会在仿真中被扣减 |
| `heat` | `int` | 初始热量，[0,100] | 每帧先减 `cool`，发射后加 `shot_heat` |
| `cool` | `int` | [0,100] | 每帧固定冷却量，可为 0 |
| `shot_heat` | `int` | [0,100] | 每次成功射击增加的热量，可为 0 |
| `requests` | `const std::vector<int>&` | 最多 10000 项，每项 0 或 1 | 0=不射击，1=请求射击 |
| 返回值 | `FireResult` | 四个字段 | `shots`/`rejected` 是统计，`ammo`/`heat` 是**末态** |

两个容易看错的点：

1. **`heat` 参数会被修改**——它不是"初始热量快照"，而是随帧推进的状态。函数内用自己的局部变量接收即可，参数按值传递，不影响调用方。
2. **空 `requests` 完全不冷却**。规范 6 明确"空请求不发生任何冷却，返回原始 ammo、heat"——冷却是**每帧**的第一步，没有帧就没有冷却。

## 3 规范逐条拆解

| 题面规范 | 翻译成代码动作 | 最容易踩的坑 |
| --- | --- | --- |
| 1 参数范围 | 无需检查，题面保证 | 自己加校验反而画蛇添足 |
| 2 每帧先冷却、负则归零 | `heat -= cool; if (heat < 0) heat = 0;` | 放在请求为 1 的分支里（请求 0 也要冷却） |
| 3 请求 0 只冷却 | `if (request == 0) continue;` | 把请求 0 也计入 rejected |
| 4 双条件才可发射 | `ammo > 0 && heat + shot_heat <= 100` | 漏 `ammo > 0`；把 `<=` 写成 `<` |
| 5 成功改三处、失败只加一 | 成功 `--ammo; heat+=shot_heat; ++shots;`；失败仅 `++rejected` | 失败时也扣弹或加热 |
| 6 空输入、计数从零、调用独立 | 循环一次不执行；局部统计变量 | 用 `static`；空请求时也冷却一次 |

## 4 核心一：冷却是"每帧无条件第一步"

```cpp
for (int request : requests) {
    heat -= cool;                  // 无条件，请求 0 也执行
    if (heat < 0) heat = 0;        // 夹到 0，不出现负热量

    if (request == 0) continue;    // 只跳过"发射判定"，不跳过冷却
    // ...
}
```

**冷却必须写在 `if (request == 0)` 之前**。如果把冷却放进"请求为 1"的分支，那么请求 0 的帧不会降温，与规范 2、3 都冲突。

还有一个隐蔽点：**拒绝帧也要冷却**。请求为 1 但资格不足时，这一帧的冷却已经发生，不能"撤回"。这正是我写自测时踩的坑（见 §10）。

### 逐帧跟踪题面样例 1

`simulate(2,90,10,20,{1,1,1})`：

| 帧 | 请求 | 冷却后 heat | 判定 | 动作 | 末态 (ammo,heat,shots,rejected) |
| --- | --- | --- | --- | --- | --- |
| 1 | 1 | 90−10=80 | 80+20=100 ≤ 100，且 ammo=2>0 | 发射 | (1,100,1,0) |
| 2 | 1 | 100−10=90 | 90+20=110 > 100 | 拒绝 | (1,90,1,1) |
| 3 | 1 | 90−10=80 | 80+20=100 ≤ 100 | 发射 | (0,100,2,1) |

结果 `{2,1,0,100}`。注意第 2 帧虽然拒绝，**热量仍从 100 降到 90**——这是下一帧能发射的前提。

## 5 核心二：资格判定与事务性

```cpp
if (ammo > 0 && heat + shot_heat <= 100) {
    --ammo;
    heat += shot_heat;
    ++shots;
} else {
    ++rejected;
}
```

两个条件用 `&&` 短路，必须同时满足：

1. **弹量充足**：`ammo > 0`。弹量为 0 时，即使热量允许也拒绝；但冷却照样发生（`simulate(0,50,10,20,{1}) → {0,1,0,40}`）。
2. **热量不超限**：`heat + shot_heat <= 100`，**等于 100 允许**（规范 4）。写成 `< 100` 会错掉所有"恰好到上限"的用例。

成功时三个动作一起做，失败时**只** `++rejected`：弹量不变、热量不变、shots 不变。这与 Q4 的"失败不留半套修改"是同一类事务思想，只不过本题的判定点更集中。

`shot_heat = 0` 是合法的：`heat + 0 <= 100` 恒成立，只要 `ammo > 0` 就能发射，`simulate(1,100,0,0,{1}) → {1,0,0,100}`。不要因为"热量没变"就误判为失败。

## 6 完整参考实现

```cpp
FireResult simulate(int ammo, int heat, int cool, int shot_heat, const std::vector<int>& requests) {
    int shots = 0;
    int rejected = 0;

    for (int request : requests) {
        heat -= cool;                       // 每帧第一步：固定先冷却
        if (heat < 0) heat = 0;             // 夹到 0

        if (request == 0) continue;         // 无请求：只冷却，不计数

        if (ammo > 0 && heat + shot_heat <= 100) {
            --ammo;                         // 成功：三个动作一起提交
            heat += shot_heat;
            ++shots;
        } else {
            ++rejected;                     // 失败：只计数，弹量与热量不动
        }
    }
    return FireResult{shots, rejected, ammo, heat};
}
```

逐关键点说明：

- 统计变量 `shots`、`rejected` 从 0 开始，且是**局部变量**，保证每次调用独立。
- `heat`、`ammo` 直接用参数变量当状态容器：参数按值传递，改动不影响调用方，也不需要额外拷贝。
- 没有 `static`、没有全局状态、没有读 stdin、没有调试输出。
- 空 `requests` 时循环一次不执行，直接返回原始的 `ammo`、`heat` 与两个 0——正好符合规范 6。

## 10 缺陷定位与修复（README 素材）

| 阶段 | 现象 | 定位 | 修复 |
| --- | --- | --- | --- |
| 写自测时 | 两条断言失败：`冷却不足仍拒绝 got={0,1,1,81} want={0,1,1,100}`；`失败后冷却再成功 got={2,1,0,80} want={2,1,0,100}` | 逐帧手算发现：拒绝帧**也执行了冷却**，热量必然下降。我写期望值时误以为"拒绝 = 什么都不发生"，把热量当成保持 100 | 修正期望值为 81 和 80；实现无需改动 |

这段的价值：**"拒绝"在本题不是"整帧无效果"**——冷却已经发生，只是射击的三个动作没做。混淆这两层会导致期望值系统性偏高。定位方法是按规范逐帧列状态表（§4 演示了格式），与程序输出对位比较。

一个配套检查：`simulate(0,50,10,20,{1})` 返回 `{0,1,0,40}`，热量从 50 降到 40 而弹量始终为 0——这条用例单独验证了"无弹也先冷却"。

## 11 常见错误对照表

| 错误写法 | 后果 | 正确做法 |
| --- | --- | --- |
| 冷却写在 `if (request == 1)` 内 | 请求 0 的帧不降温 | 冷却放循环体最前面，无条件执行 |
| 空 requests 也冷却一次 | 违反规范 6 | 冷却在 for 内，无帧则不执行 |
| `heat < 0` 不归零 | 出现负热量 | 冷却后立即 `if (heat < 0) heat = 0;` |
| 请求 0 计入 rejected | 计数错误 | `if (request == 0) continue;` |
| `heat + shot_heat < 100` | 边界用例错 | 用 `<=` |
| 漏 `ammo > 0` | 空弹也能射击 | 两个条件用 `&&` |
| 失败时 `heat += shot_heat` | 拒绝留下副作用 | 失败分支只 `++rejected` |
| 用 `static` 统计变量 | 调用间状态串味 | 局部变量，从 0 开始 |
| 返回下标或布尔 | 结构不匹配 | 返回 `FireResult{...}` |

## 12 复杂度

- **时间**：`O(m)`，`m = requests.size() ≤ 10000`。每帧常数次运算，无嵌套循环。
- **空间**：`O(1)` 额外空间，只有两个统计变量和参数当状态容器；返回值 `FireResult` 不计入。
- **数值**：所有量都在 [0,100]，`heat + shot_heat ≤ 200`，`int` 完全安全，无需宽整数。
